### (4.3.1 cut — 2026-09-24: everything below ships in this release)

### Fixed (post-launch UX, the seeded-grant case)

- **Fail-closed default for unconfigured deployments (fleet decision D20, ratified 2026-09-24).** The historical default — a deployment with NO `RAG_API_KEY` and no registry runs fully OPEN (unauthenticated listing/reads/admin) — is replaced by a fail-closed posture with exactly one backwards-compatible carve-out: an unauthenticated request binds an **anonymous registry-client identity** whose ONLY grant is the deployment's memory dataset (`MEMORY_DATASET` env, when set). Effects: `list_datasets` shows only the memory dataset (empty when unset), dataset paths 403 (401 at the password gate for the memory dataset itself), `/api/admin/*` 403, dataset creation 403 — while the memory tools keep working exactly as before via `MEMORY_DATASET` + `RAG_MEMORY_PASSWORD` (the password env is now the LAST fallback in `_resolve_memory_password`, completing the env-only single-user setup path). Public surfaces unchanged: `/`, `/manage`, `/access`, `/healthz`, `/readyz`, metrics, and self-authorizing media/staged serving (the anon check sits AFTER the public-path exemption — media serving's own password/token gate is untouched). With ANY key configured (REST, MCP keyset, registry, overlay) the normal resolution governs instead — the anon branch fires only when nothing at all is configured. MCP mirrors the posture: the middleware binds the same anonymous identity when no keys are configured; with an MCP keyset present, the presented key resolves (admin) and the gate enforces as before. Existing deployments are unaffected: any configured key (chart-managed or `existingSecret`) keeps full behavior. Covered by updated/new tests: the MCP middleware contract (anon binding with/without `MEMORY_DATASET`, MCP-keyset resolution, wrong-key 401), and the REST fail-closed shape end-to-end (memory-only listing, 403s, password-gated memory access, admin 403, public pages).

- **Delegation precedence (fleet decision D19) — per-key delegation behind an LLM gateway now works.** The PCAI LLM gateway authenticates ITSELF upstream with an admin token (`Authorization: Bearer <platform-token>`) AND forwards the caller's delegated key via a credential override (`X-API-Key: <user key>`). `resolve_presented` checked admin keys FIRST over ALL presented candidates, so the co-forwarded admin token escalated EVERY gateway request to admin — the delegated per-user identity was structurally unreachable (unfiltered listings, no ★ binding, no password sidecar; memory tools dead through the gateway even with everything else correct). Fix: header-source-aware resolution — `presented_keys_with_source()` pairs each candidate with the header that presented it, and when an `X-API-Key` candidate is present it WINS over a co-forwarded `Authorization: Bearer` (the explicit `X-API-Key` is the caller's DELEGATED identity; `Authorization` is transport/platform auth). De-escalation-only by construction: an admin-token holder can narrow itself with an X-API-Key (it could use that client key directly anyway), and an unknown X-API-Key can never escalate to the riding admin token (verified by test). Wired in BOTH middlewares (MCP `_RagClientAuthMiddleware` via the new `presented_keys_with_source`; REST middleware now collects `(key, source)` pairs across `X-RAG-Api-Key`/`X-API-Key`/`Authorization: Bearer`). Legacy single-header behavior is byte-identical (no source list → historical admin-first order, pinned by test). Covered by 5 new tests in `test_admin_registry.py` incl. the full gateway topology end-to-end (admin Bearer + delegated X-API-Key → andrew's isolated listing; memory dataset + password both resolved).

- **`list_datasets` isolation ruling (2026-09-24, reverses the D16 discovery-mode flip).** A registry key's listing shows ONLY its effective datasets — operator grants ∪ self-selections — on BOTH surfaces (REST `_rag_acl_filter_datasets` and the MCP `list_datasets` filter now compute the same D16 union; the "show all names for discovery" behaviour is removed). Access isolation is the design: a listing never surfaces names the key cannot use; users learn dataset names from their grants/admin. The per-dataset `acl_granted` stamp (the page's ✓ granted pre-check) and all tool-level union gates are unchanged. Docs updated (README, API.md, MCP.md incl. the tool table).
- **g2 values: no-expiry unlocks enabled (`rag.unlockMaxTtl: 0`).** The /access page's "No expiry (0)" lease option is now selectable on this deployment (until an explicit Lock; MCP `ttl=0` lasts until pod restart) — for a personal memory dataset's ad-hoc REST browsing. Note: the memory-seamless path remains the saved-password sidecar (a browser lease never reaches the MCP per-process cache); the endless lease is for convenience, not the memory mechanism.

- **ACL-granted datasets could not record their password ("invisibly selected") — the memory-binding gap on admin-seeded grants.** A user whose memory dataset was seeded by the admin (mint/grant via the User keys panel — comma-separated dataset list) hit a dead end: the row showed "✓ selected" (the grant), but selecting it was a silent no-op that saved NO password, so the ★ memory binding resolved the dataset while every memory call still demanded a password. Datasets NOT in the admin seed worked fine — which made the bug look like "it's already there but broken". Fix, both sides: (a) `select_dataset` on an ACL-granted PROTECTED dataset with the correct password now saves a password-only sidecar entry (`source: "acl+pw"`) — the grant stays authoritative for access (deselecting the sidecar never revokes it), and the memory tools resolve the password from it (REST + MCP responses say "Password saved … memory tools need no password now"); (b) the `/access` page PRE-CHECKS granted rows (the listing stamps `acl_granted` per dataset — "✓ granted" vs "✓ selected"), and a granted+locked protected row shows **"Add password…"** (the select form, labelled "saved for your key — password-free reads & memory") instead of a confusing repeat "Select…"; unchecking a granted row is refused with a pointer to User keys (a grant is not self-removable). Covered by 5 new tests in `test_access_store.py` (sidecar save/removal, no-password-still-minimal, verify_and_select pass-through, and the end-to-end ★-binding-resolves-password shape) — the user's exact seeded-grant scenario verified end to end (mint → listing pre-check → password → ★ → MCP resolution).

### Added

- **Admin key registry — mint and grant per-user keys from the /access page (fleet decision D17, rides the D16 knob).** The loop-closer: an ADMIN key on `/access` now gets a "User keys" panel — mint a per-user key for a name (the generated key is shown ONCE with a copy button; every other surface masks it to a `0HeC9a…` prefix), set/replace their dataset grants via a checkbox-style comma list (`*` = all), rotate a key (the old one dies immediately), and revoke — all against a file-backed overlay at `{DATA_PATH}/access/clients.json` (0600, atomic temp+replace under the cross-process fcntl lock, mtime-cached reads — the pod cannot write env, so the overlay merges: effective registry = `RAG_API_KEY_CLIENTS` env ∪ overlay, env authoritative on key conflicts, ACLs UNIONED per name so neither source can silently revoke the other). Surfaces: `GET/POST /api/admin/clients`, `PATCH/DELETE /api/admin/clients/{name}` — admin-key-only by construction (the D15 middleware denies `/api/admin/*` to registry keys; `_require_admin_identity` re-checks) and 409 when the overlay is off. `registry_configured()` now counts the overlay: an admin key resolves its identity even on a fresh deployment with an empty overlay (the mint panel needs it). The page probes `GET /api/admin/clients` once after sign-in — 200 renders the panel, 403 keeps the personal view (a registry key never sees it). Grants apply on the next request (no restart, the env-var convention). Key generation: `secrets.token_urlsafe(18)`; custom keys allowed for rotation (≥8 chars, no `:`/`;`). **Default (overlay off / `RAG_ACCESS_STORE` off): byte-identical — the module is inert.** Covered by `tests/security/test_admin_registry.py` (17 tests: copy-once masking, rotation invalidates the old key, name/dataset/key validation, env-authority on conflicts, env∪overlay ACL unions, corrupt-file degradation to env-only, and the full REST stack: admin mints → minted key authenticates + is denied the admin surface, registry key cannot mint, grant-then-revoke key lifecycle, env-client revoke refused with the pointer to the env, overlay-off 409s, validation errors).
- **Chart wiring for the D16 access store, the memory default, and the unlock TTL bound (all three charts).** `security.accessStore` → `RAG_ACCESS_STORE` (gated rendering — the default render carries NO key, byte-identical, pinned by a pruned-template comparison test), `security.accessDenySelect` → `RAG_ACCESS_DENY_SELECT` and `security.memoryDefault` → `RAG_MEMORY_DEFAULT` (both rendered only when set — empty values render nothing), and `rag.unlockMaxTtl` → `RAG_UNLOCK_MAX_TTL` (always rendered; the chart default equals the built-in default 86400 so behaviour is unchanged). The helm zero-value trap is handled explicitly: `unlockMaxTtl: 0` (the no-expiry opt-in) renders `"0"`, NOT the default — `| default 86400` treats 0 as empty, so the template keys off `hasKey` instead (caught by the render test before it could ship). Covered by `tests/full_pipeline/test_access_store_render.py` (15 render assertions across helm / helm-scale-medium / helm-scale-large: unconditional TTL render + value tracking incl. 0, access-store gating both ways, denylist/memory-default set-vs-unset, and the byte-identical default render); all example values files verified to still render unchanged.
- **Self-service dataset selection + per-identity access store (feature: the /access checkbox model — fleet decision D16, OPT-IN via `RAG_ACCESS_STORE=1`).** The ratified evolution of D15: instead of operator-only grants, a registry-key user grows their own dataset set — any authenticated key now SEES all dataset names (discovery: names only, never content) and SELECTS the ones it wants; a public dataset is a free checkbox, a password-protected one demands its correct password AS PROOF, and that password is then SAVED per identity so every REST and MCP call works without sending it again. Effective access = **operator ACL ∪ selections** (the ACL is a guaranteed floor — deselect removes only self-added widening; `RAG_ACCESS_DENY_SELECT="ds1,ds2"` datasets refuse selection outright; the admin surface and dataset creation stay D15-gated). Core: `utils/access_store.py` (stdlib-only) — one JSON per identity under `{DATA_PATH}/access/<name>.json` (shared RWX PVC, 0600, atomic temp+replace under the cross-process fcntl lock, mtime-cached reads, per-path writer lock so in-process threads serialize before flock). Surfaces: the `/access` page gains a per-dataset checkbox column with an inline password form (protected selection), a "✓ selected" state chip, and the ★ star becoming a SERVER-side per-key binding when the store is on (localStorage stays the store-off fallback); four REST endpoints (`GET /api/access/selections` — password-free by construction, `POST /api/datasets/{name}/select` — deliberately EXEMPT from the per-dataset ACL middleware pre-check since it is how access is gained, `POST /api/datasets/{name}/deselect`, `POST /api/access/memory-dataset`); three MCP tools (`select_dataset`, `deselect_dataset`, `set_memory_dataset`, 16→19); `list_datasets` (both servers) flips to discovery mode with the store on (all names + `[selected]` marks, honest "shown for discovery only" note). The saved selection password rides the existing D10 unlock machinery: MCP `_is_unlocked` and REST `_require_dataset_password` fall back to it (identity-scoped — a key can only ever read its own store), so a selected protected dataset IS unlocked for that key. Memory resolution order becomes: explicit arg → request header → the caller's saved ★ binding → `MEMORY_DATASET` env (with `RAG_MEMORY_DEFAULT` as an optional deployment-wide fallback) — **opencode can now drop `RAG_MEMORY_DATASET` / `RAG_MEMORY_PASSWORD` entirely**: paste the API key once, select your memory dataset (with its password, once), star it. Store off (default): byte-identical D15 behaviour everywhere (pinned by tests: ACL-filtered listings, fail-closed gates, selection endpoints 409). Covered by `tests/security/test_access_store.py` (29 tests: store mechanics incl. concurrent-writer serialization + corrupt-file recovery + hostile-identity-name rejection, denylist enforcement, union/floor semantics, memory binding round-trip + accessibility fail-soft, MCP gate union + tool flow end-to-end + saved-password unlock satisfaction + unchanged env fallback, and the full REST stack: discovery listing, select-no-body/select-wrong-password/select-right-password, unselected-still-403, password-free selections endpoint, deselect revocation, admin refusal).
- **`/access` page — the per-user key-holder's view (Phase 1 of the access-management plan).** A new public HTML page (like `/` and `/manage`; the page IS its own auth boundary) where a user pastes **their own** API key (sessionStorage, optional "remember on this device" in localStorage) and manages their personal access: their ACL-filtered dataset list (with the honest "n hidden by access policy" note), per-dataset unlock with a TTL selector (30 min / 1 h / 6 h / 24 h default / **No expiry (0)** — the 0 option is meaningful only on deployments that opt in via `RAG_UNLOCK_MAX_TTL=0`, see below), one-click Lock (revocation), and a ★ "use as memory dataset" marker persisted client-side (`localStorage['rag-memory-dataset']`; client-side preference this release — server-side memory-dataset binding arrives with Phase 2). The server deliberately injects NO key meta tag into this page (unlike `/`, which embeds the deployment key for its operator context): under D15 the page is used with per-user registry keys, and injecting the deployment key would leak admin credentials onto a public page. Dataset passwords are never stored by the page. Covered by `tests/security/test_access_page.py` (public under auth alongside `/` and `/manage`, no key material in the render, TTL-bound meta injection, graceful fallback when the template is missing).
- **Unlock TTL bounds via `RAG_UNLOCK_MAX_TTL` (default `86400` = the historical 24 h cap) with an explicit no-expiry opt-in.** Both unlock surfaces (REST `POST /api/datasets/{name}/unlock` and the MCP `unlock_dataset` tool) now clamp explicit TTLs to a configurable bound read per request (rotation without restart; malformed/negative values fall back to the default). `RAG_UNLOCK_MAX_TTL=0` opts the deployment into **no-expiry unlocks**: `ttl=0` caches the unlock with no deadline — REST: until `POST /api/datasets/{name}/lock` (Redis keys set without `ex`; in-memory entries use an infinity sentinel); MCP: until process restart, with the bounded-entry cache guard still applying under pressure (fail-soft — the caller re-unlocks). Bounded by default, opt-in to open: a no-expiry unlock holds a dataset's plaintext password in the unlock store indefinitely, so the knob is deliberately NOT enabled by default. The `/access` page reads the bound via `<meta name="rag-unlock-ttl-max">` so its TTL selector always matches the server. Covered by `tests/security/test_access_page.py` (default 24 h, per-call env reads, ttl=0 rejected by default on both surfaces, accepted under the opt-in, clamping, non-integer rejection, and lock-revokes-no-expiry end-to-end).
- **Contextual retrieval (feature: contextual retrieval — ingest-time LLM context injection; DECISIONS 2026-09, values-gated DISABLED by default).** For every chunk that carries real extracted text, one small LLM call — `rag.vlm`, the same text-capable ChatModel the caption path uses, **no new model role** — writes 1–2 sentences of document-level context, prepended to the chunk text as a visibly-labeled `[Document context]:` line BEFORE embedding (stage 0a½ in `aadd_to_vector_store`, right after `_preprocess_docs`, before the sub-batch loop — so the base embedding AND the text-only twins embed the contextualized text, and the BM25 lexical lane indexes it for free via `_bm25_indexable_text`). Three gate levels make "disabled by default" real: the chart knob `rag.contextual` → `RAG_CONTEXTUAL_DEFAULT` only stamps NEW datasets at create time (gated configmap rendering — a disabled deployment renders no config key and the default chart render is byte-identical across all three charts); the per-dataset `meta["contextual"]` flag (`create_dataset(contextual=…)` / `PATCH` allowlist, riding the existing caption-changed RAG-cache invalidation) gates the pipeline; and the module is a no-op without a VLM. Surfaces: a `contextual` checkbox on the dashboard's create form and dataset-detail flag row (with `<meta name="rag-contextual-default">` injected only when the deployment default is on), and `POST /api/admin/datasets/{name}/contextual-preview` — a LABELED ESTIMATE (live Qdrant count, ×2 for hybrid-capable collections since real-text chunks get context-carrying text twins, × the token math of one context call: shared preamble + chunk input + ~80 output tokens, plus the configured VLM name) shown as the UI confirm line next to the checkbox. Mechanics: the doc preamble (filename + `RAG_CONTEXTUAL_DIGEST_CHARS`, default 512, excerpt) is byte-stable per document and chunks are contextualized per document in producer order with the first call completed before its siblings fan out — vLLM/SGLang prefix caching absorbs the shared prefix; in-flight calls bounded by `RAG_CONTEXTUAL_CONCURRENCY` (default 8, ≤0 unbounded; the `MODEL_EMBED_MAX_CONCURRENCY` semaphore pattern). Skips: pure-media docs (no `_has_real_text` — a context line would newly count as real text and flip the twin gating; media docs already have the caption-twin path), `memory_kind`-tagged docs (memories stay verbatim), and twins; fail-open everywhere — any LLM error stores the plain chunk + a non-fatal ingest warning (the caption-skip discipline), never failing the ingest. Introspectability: every stored point carries `metadata.contextualized: bool`, and `meta.json` records `contextual` next to the embedder fingerprint — a later mode mismatch WARNS (never errors; mixed-embedding datasets are explicitly permitted per the decision; Recreate makes a dataset uniform). `DATASET_SCHEMA_VERSION` deliberately NOT bumped (no collection-shape change). **The honest enable story: affects NEW ingests only** — re-uploading existing files hits content-hash dedup (the context changes the embedding, not the file hash), so adopting existing content = Recreate, the existing flow. Covered by `tests/full_pipeline/test_contextual_retrieval.py` (37 tests: contextualizer unit tests on a stub VLM — prepend+stamp, fail-open, empty completion, preamble stability, concurrency bound, first-call-before-fan-out, prompt cap, media/memory skips, no-VLM identity; end-to-end ingest through the in-memory and local-Qdrant stores incl. the BM25-lane flow and the caption-twin exclusion; the flag rail create/PATCH/cache-invalidation; preview math incl. the twin multiplier and the Qdrant-failure fallback; the fingerprint warn-not-error cases; template + meta-injection gating + configmap gating across the three charts).
- **Weighted-RRF per-dataset defaults (feature: weighted RRF — the "home page weights" dataset-defaults slice).** `meta.json` gains `rrf: {dense_weight, sparse_weight, k}`: per-dataset rank-space lane tilts for the hybrid dense+BM25 fusion (qdrant scores each lane `1/((pos+1)/w + k − 1)` — a tilt, NOT a score multiplier). Resolution order per search is explicit caller override > dataset default > global default (1.0/1.0, unpinned k), and a dataset default that equals the global default is stored as *absent* so the executed request stays byte-identical to the historical `FusionQuery` form (the k-default trap: emitting an `RrfQuery` for a default would pin the client's implicit k and silently change rank arithmetic). Surfaces: `create_dataset(rrf=…)` + `PATCH /api/datasets/{name} {"rrf": …}` (clamped like the REST/MCP search slices — weights 0.0–10.0/3 decimals, k 1–1000; a global-default or empty payload removes the stored default), the home page (create-form weight inputs with deployment-default placeholders, dataset-detail edit row with the rank-space/multimodal-exclusion tooltip, `<meta name="rag-rrf-default">` injected from `RAG_RRF_DEFAULT`), the MCP `search_dataset` tool (dataset default applies when the caller passes no weight; the `rrf` block reports the effective parameters), and the deployment knob `rag.rrfDefault` → `RAG_RRF_DEFAULT` (`"dense,sparse[,k]"`, **disabled by default** — stamps NEW datasets at create time only, existing datasets untouched; default chart render verified byte-identical across all three charts). Ruling preserved: caller weights win uniformly; federated search ignores per-dataset defaults (pinned by test — the fan-out runs the default fusion form even when `meta["rrf"]` is set). Existing datasets adopt defaults via PATCH only; no recreate, no schema bump. Covered by 12 new tests in `test_hybrid_search.py` + 4 in `test_create_dataset_endpoint.py` (resolution order, RrfQuery-emission rules, PATCH validation/clamps, env stamping on/off, federated ruling, MCP tool, REST create, UI render incl. `node --check` on every script block).
- **Embedder alias groups** — `models.embedder.extra.alias` (a model id, a list, or a comma-separated string) declares ids that must be treated as THE SAME embedder by the dataset fingerprint guard, e.g. a quantized (FP8) redeploy of the same base model: datasets indexed under an aliased id keep working after the swap without a recreate. Aliases excuse the model **name** only — a dimension mismatch still fails loudly. Flows through the existing `MODEL_EMBEDDER_EXTRA` JSON plumbing, so no chart/template changes are needed. Covered by `tests/full_pipeline/test_embedder_compat_guard.py`; the staging fix is covered by regression tests in `test_import_dataset.py`.
- **Watched S3 sources** (feature: watched sources; DECISIONS.md 2026-09 — values-gated, OFF by default, S3/MinIO prefixes only). Three pieces:
  - **The reconciler CronJob** (`helm/templates/watched-sources-cronjob.yaml`, all three charts): with `watchedSources.enabled` the chart renders a CronJob that, on each tick and serially per source, POSTs the configured `s3://` prefixes to `POST /api/datasets/{dataset}/batch-urls` with `{"sync": true}` and the deployment key as `X-RAG-Api-Key` (from the model-keys Secret via `envFrom`), then polls the ingest job to completion so a slow embed batch can never overlap the next tick (`concurrencyPolicy: Forbid`). Same app image, config+model-keys `envFrom`, and pod hardening as the backup cron; one failing source is logged and never kills the run. Values are validated at `helm template` time — non-`s3://` prefixes, single-object `s3://bucket/file.ext` URLs (mirroring the server's `_sync_prefixes` refusal), wildcards/query strings/whitespace, missing `dataset`/`prefixes`, duplicate datasets, unknown reserved `type:` values, and an empty sources list all **fail the render**, not the 3 a.m. cron log. Default (`enabled: false`) renders nothing — verified byte-identical default render across all three charts.
  - **The per-dataset ETag/Size skip state** (`files/.watched_state.json`, the feature-carrying part): on sync paths `add_urls_batch` now consults a sidecar next to `.hashes.json`/`.ingested_hashes.json` recording, per object key, the ETag+Size of the last successfully ingested version. A listed object whose ETag+Size still matches is dropped from the download set **before any bytes move** — no re-download, no re-embed attempt (previously every sync tick re-downloaded every object and let the content-hash dedup discard the identical bytes). The state is written after the batch, under the same `_cross_process_lock` discipline as the other sidecars (atomic promote, mtime-cached reads), for exactly the objects whose ingest demonstrably succeeded (stored chunks or a content-hash dedup skip) — a failed/zero-output object stays unrecorded and is re-attempted next tick, and same-basename collisions inside one batch are never recorded (fail-soft over false skips). Content changed under the same key flips the ETag and re-ingests (ETag+Size together is the fingerprint; multipart-upload ETags are opaque, so ETag alone would not do). Sync's prune half forgets the fingerprints of upstream-deleted sources so the documented pruned-and-reappeared heal keeps working; `sync_dry_run` reports the split as `would_download` vs `unchanged` (plus the existing `would_ingest`/`would_prune`). The state is an optimisation, never a correctness gate: a corrupt/missing file degrades to re-downloading everything; once state exists, deleting a source's documents out-of-band sticks (the reconciler no longer resurrects them — documented). Dataset delete/Recreate clears it alongside the dedup hashes. Non-sync URL ingest never consults the state. Backed by `tests/full_pipeline/test_s3_sync.py` (11 new tests: unchanged-skip, ETag-change re-download, new-object ingest, failed-object non-recording, prune-forget interplay, concurrent-writer lock, recreate-clear, corrupt-file degradation, dry-run split, docstring regression, non-sync passthrough) and `tests/full_pipeline/test_watched_sources_render.py` (22 render assertions incl. the byte-identical-disabled check).
  - **The backup-cron 401 fix** (verified latent bug from the implementation review): `helm/templates/backup-cronjob.yaml` sent no `X-RAG-Api-Key`, so under `security.apiKey` every scheduled backup call (datasets list + export download) returned 401 and the cron "worked" only by exporting nothing. Both httpx calls now present the deployment key from the same model-keys Secret (all three charts), with a loud warning when the key env is empty.
- **`_list_s3_prefix` docstring corrected** (verified doc bug): the listing has always been **recursive** — it paginates `list_objects_v2` with the `Prefix` filter only, walking the whole subtree — but the docstring claimed "only the immediate level is listed". The docstring now states the actual behaviour (which is exactly what S3 sync and watched sources rely on); a regression test pins it.


### Fixed
- **The vendor-label ClusterPolicy no longer matches Pod kind — the undeletable-pod incident cannot recur (G2 2026-09-24).** The chart's pre-install ClusterPolicy (`add-vendor-app-labels-<release>-<chart>`, `templates/kyverno.yaml` in all three variants) stamped `hpe-ezua/type: vendor-service` + `hpe-ezua/app: <chart>` on Pods/Deployments/Services in the release namespace. The EzAF platform ships its own admission policy (`assign-custom-scheduler-for-ezua-user-vendor-pods`, failurePolicy=Fail via the shared Kyverno resource-mutating webhook) that selects pods by exactly that `hpe-ezua/type` label and stamps `spec.schedulerName: scheduler-plugins-scheduler` on EVERY admission — CREATE and UPDATE. A labelled pod created before that stamping (or otherwise carrying `default-scheduler`) becomes **undeletable**: every update — the Job controller's `batch.kubernetes.io/job-tracking` finalizer removal, `kubectl delete pod`'s deletionTimestamp write — gets schedulerName rewritten in the request, and pod-update validation rejects the immutable-field change ("pod updates may not change fields other than ..."). Confirmed live: two mm-rag watched-sources cron pods carried orphaned finalizers for 24–35 h, the Job never reached Complete, and `concurrencyPolicy: Forbid` suppressed 145 cron ticks until the stale Job was deleted by hand; `--force`, finalizer-strip patches, and value-carrying merge patches are all rejected the same way (the validator compares live vs post-webhook objects). The labels exist for EzUA console app-discovery, which reads Deployment/Service objects — Pods never needed them. The policy now matches **Deployment + Service only**; pod templates are untouched and never match. Deploying this chart version permanently immunizes the release against the platform policy. Covered by `tests/full_pipeline/test_kyverno_vendor_labels_render.py` (12 render assertions across the three charts: policy renders, kinds == [Deployment, Service] exactly, no Pod kind ever, labels still land on metadata of the right objects). One-time cleanup for already-stuck pods (the `hpe-ezua/type` label on a Succeeded pod keeps it matched on update): strip the LABEL along with the finalizer in one patch — `kubectl patch pod <p> --type=json -p='[{"op":"remove","path":"/metadata/finalizers"},{"op":"replace","path":"/metadata/labels/hpe-ezua~1type","value":"__removed__"}]'` — after which the update no longer matches the platform policy and the pending deletion completes; see `.dev/s3watch/STUCK_PODS_FIX.md`.
- **Concurrent preprocessing can no longer corrupt stored media ("the video can't be played because the file is corrupt").** `_preprocess_video_file` wrote ffmpeg's output directly onto the final shared `*_preprocessed.mp4` path — no temp file, no lock, and only a `size > 0` check. With multiple `rag-mcp-server` replicas on the shared dataset PVC (and three independent call sites: ingest-time, query-time `describe_media`, staged-file preprocessing), two finalizations racing on one path splice two `moov` atoms together and leave an `mdat` overrunning EOF: the file parses at the head, so indexing succeeds, but every player refuses it. `_preprocess_image_file` and `_truncate_audio_file` had the same pattern, and `_split_audio_segments` wrote deterministic `{stem}_segment_NNN` names straight into `files/`. All four writers now produce into a unique hidden temp location (extension preserved — ffmpeg infers the muxer from it; the segment muxer works in a temp dir and moves validated segments in), validate before promoting (ffprobe streams+duration plus an MP4 top-level atom walk that flags truncation and duplicated `moov`; full PIL `verify()` for images), and promote atomically (`os.replace` / per-segment renames under the files-dir lock); a writer also skips work when a *valid* result already exists (idempotency), so replicas converging on one file don't redo each other's work. Diagnosed against the two corrupt preprocessed videos in `andrew-test-dataset` (originals were byte-perfect; reproduced the exact moov/moov/free/mdat-overrun signature with two local concurrent transcodes).
- **New repair path for already-corrupted preprocessed media.** `DatasetManager.repair_preprocessed_media()` scans a dataset's `files/` directory, validates every `*_preprocessed` sibling against its tier-1 original, and re-runs preprocessing for each broken copy (guarded by the files-dir cross-process lock, unlink-first so the writers' valid-sibling check can't skip regeneration). Exposed as `POST /api/admin/datasets/{name}/repair-preprocessed` with `?dry_run=true` for a report-only pass. Synchronous and re-embed-free: only broken files are re-transcoded, so it returns the full report directly. Covered by `tests/full_pipeline/test_preprocess_atomicity.py` (11 tests: validator truncation/duplicate-moov/healthy cases, the deterministic 3-writer race, idempotency, regenerate-on-broken-sibling, failed-transcode promotion guard, image atomicity, and the repair routine including dry-run and missing-original cases).
- **Derived media files are served with `Cache-Control: no-cache`.** The file route sent no cache policy, so browsers heuristically cached `*_preprocessed` URLs and kept serving stale (historically: corrupt, pre-repair) bytes for days without revalidating — repaired files looked "still corrupt" even though the server held healthy bytes with a fresh etag. Derived files (`*_preprocessed`, `*_segment_*`, `*_truncated`) now force conditional revalidation (FileResponse already sends etag/last-modified), so regenerated bytes are picked up immediately; originals (content-hash names, immutable) cache normally.
- **`.webm` (and other incompatible containers) are no longer transcoded — the last generator of corrupt preprocessed files.** `_preprocess_video_file` always emits libx264+aac, but ffmpeg picks the output muxer from the file extension, and the WebM muxer cannot legally carry that codec pair. Every webm preprocess was therefore doomed: ffmpeg wrote the container header and died on the first packet (or burned the full 300s timeout on large files), leaving a tiny EBML stub that passed the old `size > 0` check and got promoted — found live as a 39-byte "preprocessed" sibling of a 654 MB webm in `andrew-test-dataset` (dry-run of the new repair endpoint surfaced it). The writer now short-circuits for containers that cannot hold the output codec pair (`.webm` etc.; `.mp4/.m4v/.mov/.mkv` proceed); embedding is unaffected since frame extraction decodes the container regardless. `repair_preprocessed_media` reports such files as expected failures (stub removed, original kept) instead of silently re-promoting.
- **Creating a dataset with a space in the name no longer fails with an opaque HTTP 500.** `POST /api/datasets` only mapped `FileExistsError`, so the `ValueError` that `_validate_name` raises for `"my dataset"` escaped as an unhandled 500. The endpoint now auto-converts whitespace runs to `_` (a hand-typed `"my dataset"` becomes `my_dataset` — the obvious intent) and maps remaining validator rejections (e.g. `bad name!`) to a proper HTTP 400 carrying the validator message; the admin import endpoint already behaved this way. The dashboard name field converts as you type, so the form always shows the name that will actually be created. Covered by `tests/full_pipeline/test_create_dataset_endpoint.py`.
- **Dataset listings are ordered alphabetically regardless of case.** `DatasetManager.list_datasets` sorted the datasets directory with a plain ASCII sort, so every uppercase-initial name jumped ahead of all lowercase ones (the dashboard showed `MLS` above `alejandro-memory`). The listing key is now `(name.lower(), name)` — case-insensitive alphabetical, with the raw name as a deterministic tie-break so a hypothetical `MLS`/`mls` pair stays adjacent, uppercase first. Cursor pagination resumes with the same key (the token is pre-keyed for the keyed bisect), and the fix flows to every surface that renders the server order: REST `/api/datasets`, the MCP `list_datasets` tool, the dashboard, and the OpenWebUI dataset hint. Covered by `test_list_datasets_orders_case_insensitively` / `test_list_datasets_cursor_walk_survives_case_ties` in `tests/full_pipeline/test_wave4_performance.py`.
- **Export / documents listing are no longer blocked by the embedder fingerprint guard.** The guard fired inside `stream_all_documents` / `list_documents` / the documents-download stream, so after an embedder swap a mismatched dataset answered HTTP 409 on every payload read — making the documented export→import recovery impossible without out-of-band PVC surgery. Payload-only reads (dataset listing, `GET /documents`, export, documents download) now run with `check_embedder=False`: they embed nothing, and re-embedding happens on the import side. Search/ingest keep the guard.
- **Dataset export no longer fails with an empty HTTP 200.** The streaming export sent response headers before the generator produced anything, so a failure inside the stream surfaced to the client as a 0-byte 200 (Starlette: "Caught handled exception, but response already started") instead of the real error. The collection is now resolved (one-point probe scroll) before the response starts, converting the common failure modes (missing dataset/collection) into proper HTTP errors.
- **Import-with-overwrite no longer destroys the original on a bad archive** (delete-then-fail ordering): `prepare_import` deleted the target dataset *before* unpacking, so an archive that failed mid-extract or turned out to be unrestorable ("nothing to restore") left the target gone. Restores now stage into a hidden `.<name>.importing-*` sibling dir and swap only after the archive is fully unpacked and a restorable mode is determined; a staging failure cleans up the staging dir and leaves the original dataset untouched.

## [3.6.3] — 2026-09-11

### Fixed
- **Hybrid search scores were mislabeled as embedding similarities** — the "why is every memory-recall score exactly 0.5?" bug. Text queries on bm25-capable collections run as Qdrant RRF-fusion requests whose score is rank arithmetic (`Σ 1/(rank+2)` per lane, K=2) — not a cosine similarity. The fused value passed through `_points_to_docs` verbatim and `_format_retrieval_result` printed it as `score: %.4f`; worse, with no reranker running it was **aliased into `embedding_score`** in the MCP result JSON, so callers read `embedding_score: 1.0` for a short query vs an 8k-token chunk (a structurally impossible cosine — that 1.0 is "#1 in both lanes") and `0.5` for a certain keyword hit that won exactly one lane and missed the other lane's top-k. That single-lane-win pattern is the modal outcome for memory/session-history stores, where the dense and BM25 lanes disagree at rank 1 almost every query (boilerplate-heavy near-duplicate chunks + rare-token queries are dense noise), which is why the same handful of discrete values (0.5 / 0.3333 / 0.25 / 0.6667 / 1.0) kept recurring. `_arerank_with` had the same defect: it stamped the pre-rerank score as `_embedding_score` on every path, so even reranked hybrid results reported the RRF value as the embedder cosine.

### Added
- **Honest score labeling across the retrieval surface**: every result now carries a `score_kind` (`rrf` | `cosine` | `reranker`) in both the formatted context (`[Result 1] (rrf score: 0.5000)`) and the JSON entries; hybrid responses additionally get an explanatory header ("rank-based, not similarity — trust the order, not the magnitude"). `embedding_score` is now `null` instead of an aliased fused score, and the pre-rerank value travels as `retrieval_score` when a rerank ran. The vector store stamps `_score_kind` on hybrid-lane results in `similarity_search_with_score_by_vector_batch` (dense-only results default to cosine); `_arerank_with` labels the incoming score truthfully per lane.
- **True dense cosines for hybrid results at zero extra query cost**: Qdrant's fusion API cannot return per-lane scores (verified against qdrant-client 1.19.0 models and the hybrid-queries docs: `QueryRequest`/`Prefetch` expose no intermediate-score surface and `ScoredPoint` carries exactly one `score`) — but the fusion request itself can carry back each point's **stored dense vector** (`with_vector=["dense"]`; Qdrant fetches vectors by id after fusing). Hybrid requests now do exactly that, and the store recomputes the true dense cosine client-side against the query embedding it already holds — no second query, no second HNSW traversal — including for sparse-only hits the dense lane never ranked (exactly the score fusion hides). Kill-switch: `RAG_HYBRID_EMBEDDING_SCORES=0` skips the vector transfer. Covered by `test_hybrid_results_carry_true_dense_cosine`, which cross-checks the recomputed cosine against a direct dense-only search over the same stored vectors.

- **Archive-bomb bounds**: `ARCHIVE_MAX_TOTAL_BYTES`, `ARCHIVE_MAX_MEMBER_BYTES`, `ARCHIVE_MAX_ENTRIES` are audited from the archive headers *before* extraction (recursively for nested archives).
- **Media path allowlist**: `MEDIA_ALLOW_PATH_PREFIXES` constrains which `file://` / local paths the MCP media tools read.
- **Signed media tokens**: when `MEDIA_TOKEN_SECRET` is set, media URLs carry a short-lived HMAC `?token=<expiry>.<sig>` (TTL `MEDIA_TOKEN_TTL`) instead of the clear dataset password; the file-serving endpoint validates tokens.
- **REST API auth**: `RAG_API_KEY` enables `Bearer`/`X-RAG-Api-Key` enforcement over `/api/*`, with probes/pages/media-serving exemptions.
- **Password throttling**: per-identity failure counters (`PW_MAX_FAILURES` / `PW_FAIL_WINDOW`) rate-limit unlock/verify/search flows.

### Post-audit follow-ups

- **PyMuPDF import migration**: PDF extraction now uses `import pymupdf` instead of the deprecated `fitz`, silencing the "`fitz` API is deprecated" startup warning (PyMuPDF ≥ 1.24 exposes the new module under `pymupdf`).
- **`qdrant-client` floor pinned to ≥1.19**: the gRPC auth interceptor only guards its deprecated `asyncio.iscoroutinefunction()` call since 1.19; older releases emit a `DeprecationWarning` once per Qdrant search on Python 3.14 (re-logged at INFO by the MCP SDK). `qdrant-client>=1.19.0,<2` prevents a future build from regressing to a warning-spamming release.
- **MCP sidecar probes**: the MCP server now serves `/healthz` (SSE and streamable-http transports) and the Helm deployment configures startup/liveness/readiness probes for the sidecar container.
- **`describe_media` modality detection**: URLs are classified by their *path* extension (query/fragment ignored), so `…/photo.jpg?hmac=…` is recognised as an image even though the string does not end in `.jpg`; for extension-less CDN URLs it falls back to a bounded network probe (Content-Type + first-chunk magic bytes), and extension-less local files / `data:` URLs are sniffed via magic bytes /
  MIME prefix. A new optional `media_type` parameter ("image"/"video") lets the caller force the expected modality, and the query wording (e.g. "describe the image") is used as a low-confidence hint when detection is ambiguous. The response now reports the resolved `media_type`.
- **Hash-index cache**: `.hashes.json` reads are mtime-cached per process so large file sets are not re-read/re-parsed on every upload.
- **No base64 media in the LLM result JSON**: `search_dataset`/`search_memory` result JSON no longer carries heavy tier-3 `image`/`video`/`audio` base64 data URLs. The Postprocessor still consumes them internally to generate descriptions, but the JSON handed back to the LLM drops a media key when no tier-2 `preprocessed_*` ref exists to attach a viewable URL — a matched video segment previously
  dumped megabytes of `data:video/mp4;base64,...` into a text-only LLM's context (tens of thousands of wasted tokens). Tier-2 refs are still substituted and converted to signed HTTP URLs as before.
- **Model connectivity monitoring**: the embedder is probed in the background every `MODEL_HEALTH_INTERVAL` (default 60 s); `/api/admin/health` exposes `models.embedder` status. The embedder gate drives the **readiness** probes (`/readyz` on the API and a new `/readyz` on the MCP sidecar, which the Helm charts now use for the MCP readiness probe) after `MODEL_HEALTH_FAIL_THRESHOLD` (default 3)
  consecutive failures — liveness is untouched, so a remote vLLM/SGLang embedder outage drops the pod out of rotation without a restart loop. A new `GET /api/admin/connections` endpoint live-checks every configured model (`healthy` / `not_provided` / `unhealthy`), and the management page gained a "Test connections" button plus a live embedder status indicator.

### Caption twins for media (dual-embedding ingest)

- **Caption twins for image/video/audio**: pure-media docs (whose text is a media placeholder + an ingest-time VLM/ASR caption) now get a *second* embedding — the same media embedded **with** the caption text — in addition to the base media-only embedding (which strips captions via `_strip_embed_caption`). Caption wording is therefore searchable by text queries that the raw-media embedding would
  miss. Gated by `_media_caption_twin_needed()`: created only when the embedder supports the doc's media modality AND a caption is present. If the embedder can't embed the media but a VLM/ASR module can, the Preprocessor collapses the media to caption text and embeds that (existing behaviour, unchanged); if neither supports it, the media is skipped entirely. Twins share the parent's `(source,
  page, chunk_index)` identity and are tagged `_twin=True`, so retrieval `_dedup_twins()` still prefers the parent when both match.
- New offline tests: `tests/full_pipeline/test_twins.py` (helper gating + end-to-end ingest through the in-memory store with a stub embedder).

### Ingest-warning surfacing fix

- **Skip/caption warnings now reach the UI**: ingest warnings (media dropped because neither the embedder nor a VLM/ASR supports it, ASR/VLM unavailable, caption skipped) are collected per request and returned to the frontend as `warnings` — single-file uploads and `POST /documents` return them in the response body; batch-files/batch-urls attach them to the job result the UI polls. Previously the
  collector (a `contextvars.ContextVar`) was invisible to the thread-pool/background-loop workers that actually run ingestion, so the `warnings` list always came back empty in every path. The four ingest call sites in `api_server.py` now submit through `_submit_with_context`, which copies the request context into the worker threads. Regression test: `tests/full_pipeline/test_ingest_warnings.py`.

### Audit clean-up (Low-severity)

- **PIL file handle released** (`dataset_manager.py`): `Image.open(...)` in `_preprocess_image_file` now runs under a `with` block, so the decoded image's file handle is closed right after the size check instead of being left to GC.
- **Media-payload strip no longer silent** (`dataset_manager.py`): `_strip_media_payloads` logs a warning when the Qdrant retrieve fails or a `set_payload` group fails, instead of bare `return`/`continue` swallowing the error.
- **Deprecated FastAPI startup hooks removed**: `api_server.py` and `embed_batcher.py` replaced `@app.on_event("startup")` with a `lifespan=` context manager (the `on_event` API is removed in FastAPI 0.99+). Both apps still run the same eager init / config-watcher / health loop / upload-prune work at startup; verified via `app.router.lifespan_context`.

### Unified "skip entirely" drop + on-disk cleanup

- **Uniform drop rule for all media types** (`rag_system.py`): audio, image and video now behave identically when the embedder can't ingest the media and no VLM/ASR can convert it to caption text — the media is removed and, if nothing embeddable remains (no supported media, no caption text, no real text — a bare `[Video: x.mp4] [0s–32s]` placeholder doesn't count), the whole document is
  **omitted** and logged + surfaced as an ingest warning. Previously image (kept but never embedded) and video (left a placeholder-only doc) diverged from audio's drop.
- **On-disk cleanup of dropped files** (`dataset_manager.py`): when every document a file produced is dropped, the stored copy in `files/` (and its `*_preprocessed` tier-2 sibling) is deleted and its content-hash entry forgotten — a file that can never be used no longer occupies PVC space. Deleting is guarded by a vector-store reference check (`_file_referenced`), so a file still referenced by any
  Qdrant point is never orphaned; remote (URL) ingests are never deleted. Wired into both the batch consumer and the single-file/URL ingest path. New offline tests: `tests/full_pipeline/test_ingest_drop_cleanup.py`.

### Deployment fixes (found in mm-rag production)

- **Recreate now actually re-embeds** (`dataset_manager.py`): `recreate_dataset` clears the per-dataset ingest-dedup index (`.ingested_hashes.json`) before re-processing, so it no longer skips every previously-ingested file as "already ingested" and leaves the freshly-dropped collection empty. Previously, "Recreate" dropped the Qdrant collection and then stored **0** documents (files are skipped
  by content-hash dedup on the second pass).
- **Job progress is now shared across workers/pods** (`api_server.py`): `_UploadJobTracker` mirrors each job to Redis (when `REDIS_URL` is set) with a 6h TTL, so the poll-based `upload-status` endpoint answers from any API process. The in-memory-only tracker returned `404 Job … not found` under the scale chart (4 replicas × 4 gunicorn workers) whenever the load balancer routed the progress poll to
  a different process than the one that created the job — breaking progress for batch uploads and recreate. Falls back to in-memory-only when Redis is unavailable.
- New offline tests: `tests/full_pipeline/test_job_tracker_recreate.py`.

### Known limitations / future work

- The RAG `need_media` flag is still on for *every* search when a VLM is configured, even when ingest-time captions let the Postprocessor skip the VLM call (the skip happens after the payload transfer). A two-pass fetch (lightweight first, then re-fetch only the docs that will actually hit the VLM) would eliminate the residual traffic — deferred.
- `.hashes.json` is kept as a JSON + fcntl format (not SQLite) because the RWX PVC is NFS-backed, where in-process SQLite locking is unreliable.
