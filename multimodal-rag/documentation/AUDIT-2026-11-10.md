## P1 — fix before the next release

### P1-1 — New client-side hybrid path stamps `_score_kind="rrf"` on DENSE-ONLY results
`src/multimodal_rag/vector_store.py:1351-1359` (contrast the legacy branch at `1401-1413`)

```python
1351:                for doc, _ in per_query:
1352:                    doc.metadata["_score_kind"] = "rrf"        # <-- unconditional
1353:                    if applied:
1355:                        doc.metadata["_rrf"] = {...}
```

`hybrid` is true whenever the *collection* supports a BM25 lane, but `_bm25_stats()` returns
`None` for an empty index or a lost/corrupt `.bm25_stats.json` sidecar (`vector_store.py:1113`).
In exactly that case `_query_requests_laned` emits a **single dense request** (`644-661`),
`_execute_laned` returns raw cosines (`1482-1486`), and the outer loop stamps every one of them
`"rrf"`. The legacy path in the same function deliberately leaves them UNSTAMPED. Consumers
then mis-rank: `federated_score_kind`/`lane_rank_scores` (`rag_system.py:274-285,340`) group
raw cosines with genuine RRF sums — re-opening 2026-10-16's P1-3 for the cold-sidecar case —
`_arerank_with` (`rag_system.py:380-383`) mislabels a cosine, and REST/MCP report
`score_kind:"rrf"` + `rrf.applied=true` for a search that never fused.

**Fix:** make the stamp per-query — `fused = len(grouped[q_idx]) == 2` — and only stamp when
fused. Keep `_stable_tiebreak` unconditional.

### P1-2 — Every hybrid query prefetches 200 candidates per lane *with payloads and dense vectors* (~40x)
`src/multimodal_rag/vector_store.py:61,100,585-606,1194-1204`; caller default `rag_system.py:3421`

```python
 61: _DEFAULT_PREFETCH_FLOOR = 200
100:     return max(int(k), _prefetch_floor())
587:     vec = ([dense_using] if dense_using is not None else True) if want_dense_vectors else False
594:                     with_payload=with_payload,   # lightweight = exclude only image/video
595:                     with_vector=vec,             # <-- dense vectors on the SPARSE lane too
```

At HEAD these requests used `limit=k`; the dirty diff replaces that with `max(k, 200)` on **both**
lanes. For the default `top_k=10` that is ~400 payload rows + ~400 dense vectors per query
where 10 rows moved before; the lightweight selector (`_lightweight_payload_selector`,
`vector_store.py:313-323`) excludes only `metadata.image`/`metadata.video`, so `page_content`
and all metadata still transfer. 390 of every 400 rows are discarded by `scored[:limit]`.
Federated search multiplies by dataset count; `RAG_PREFETCH_FLOOR` is env-only and rendered by
**no** chart, so every deployment inherits it silently.

**Fix:** (a) `with_vector=False` on the sparse lane, fetch vectors only for the ≤k survivors;
(b) a real payload include-list for collapsed-out rows; (c) render `rag.prefetchFloor` in the
charts; (d) measure p95 search latency before/after on a large collection.

### P1-3 — SSO `next` parameter is interpolated raw into `Set-Cookie` → response-header splitting
`src/multimodal_rag/api_server.py:7351-7363` + `utils/oidc_sso.py:487-492`

```python
# api_server.py:7352
    target = oidc_sso.safe_next_path(next)
    parts = [f"{oidc_sso.state_cookie_name()}={state}|{target}", "Path=/", ...]
    resp.headers.append("set-cookie", "; ".join(parts))

# oidc_sso.py:490
    if raw.startswith("/") and not raw.startswith("//") and "\\" not in raw:
        return raw          # <-- no control-character check
```

`/oauth/login` is in `_PUBLIC_PATHS` (`api_server.py:1046`) and `next` is a plain
percent-decoded query parameter, so `?next=/x%0d%0aSet-Cookie:%20evil=1` reaches the header
value intact. uvicorn's default httptools writer emits header values verbatim → header/response
splitting from an unauthenticated route (cookie tossing / session fixation; XSS where the block
can be terminated). Confirmed with a logic snippet by the zone; the guard accepts the payload.
Gated on SSO being configured — the documented G2 shape.

**Fix:** reject `\r\n\0`/non-printable in `safe_next_path`, percent-encode the target before it
enters the cookie, and build the cookie with the already-defined
`_sso_state_cookie_headers()` (`api_server.py:7308`, currently unused by this handler).

### P1-4 — P0-1's blind spot: the D10 caller id is still header-derived from the bare flag, and it keys both the throttle and an **unbounded** unlock cache
`src/multimodal_rag/api_server.py:510-519` (credential gate at `1365-1370`), amplifier `595-596`

```python
# api_server.py:510  (_request_identity) — bare flag, NO enforcing-proxy assertion
    if _TRUST_PROXY_IDENTITY:
        for header in ("X-Auth-Request-Email", "X-Auth-Request-User", "X-Email", "X-User"):
            ...
            return val.strip()
# api_server.py:595  — unbounded dict holding the PLAINTEXT password
    with _UNLOCK_CACHE_LOCK:
        _UNLOCK_CACHE[(dataset, cid)] = (expiry, password)
```

2026-10-16's P0-1 fix correctly requires a positive enforcing-proxy assertion before a header may
resolve a **credential**. The throttle/unlock path deliberately keeps "the flag alone"
(`_trust_proxy_identity(request=None)`, `api_server.py:964-980`) — whose docstring claims "the
P0-1 remediation makes the header trustworthy again by pairing it with an enforcing-proxy
assertion". **It does not.** Consequences on any pod reachable without traversing the gateway
(the exact threat model P0-1 was fixed for):
1. **Unlimited password guessing** — rotate `X-Auth-Request-User: a1, a2, …` and every attempt
   gets a fresh `_pw_fail_buckets` bucket, so the 429 never fires.
2. **Unbounded memory/Redis growth** — each successful unlock with a new `cid` adds
   `_UNLOCK_CACHE[(dataset, cid)]` holding the plaintext password, with no cap for
   `RAG_UNLOCK_MAX_TTL` (default 24 h). The MCP twin *does* cap it
   (`_bounded_cache_put(_unlocked, …, _MAX_UNLOCK_ENTRIES)`, `mcp_server.py:440,578`).

**Fix:** (a) gate the header source on `_enforcing_proxy_precondition(request)` in
`_request_identity`; (b) reuse `_bounded_cache_put` for `_UNLOCK_CACHE` and cap its length.

### P1-5 — MCP `end_short_term_memory` is a dataset existence + owner + kind oracle — the exact ordering REST calls a bug
`src/multimodal_rag/mcp_server.py:3496-3535` vs `api_server.py:2370-2401`

```python
# mcp_server.py:3499  "F4: existence FIRST."
            if not meta: raise ToolError(f"Dataset '{dataset_name}' not found.")
            ...
```

**Fix:** mirror REST — ownership gate first with ONE nameless refusal, then existence, then kind;
update `tests/security/test_stm_surface.py` to pin parity.

### P1-7 — `fleet_reconcile` mirror-pair reconcile promotes MIRROR content into the fleet source, inverting its own contract
`src/multimodal_rag/utils/fleet_reconcile.py:368-394` (behaviour) vs `:24-26` and `:457-460` (contract)

```python
# fleet_reconcile.py:469 — the mirror pair is passed as (source=repo_copy, copies=[mirror])
    ok &= self.reconcile_file(f"{rel} (mirror)", repo_copy, [mp])

# :368 — so "repo_changed" is the MIRROR, and the winner is promoted into the repo copy
        if not src_changed and repo_changed:
            winner = repo_changed[0][0]
            if self.run: promote(winner, source)
```

The docstring says *"a mirror is never allowed to redefine fleet content — only a REPO copy can
promote"*, and the inline comment at `:457-460` says *"the repo copy wins REPAIR"*. The code
does the opposite: when the mirror alone moved, `promote()` writes the **mirror's** bytes into
the repo copy's inode, and the next pass propagates them to every linked repo. Both named
failure modes are inverted — a Syncthing peer-write reversion of a delivery-tree file promotes
**stale content fleet-wide**, and a peer edit to a mirror redefines fleet truth.

**Fix:** for mirror pairs, when the mirror moved and the repo copy is at baseline, `relink`
the mirror from the repo copy and record state — never `promote(mp, repo_copy)`.

### P1-8 — `hardlinker.py --prune --force` applies no ignore/hidden rules to the orphan walk → deletes `dest/.git`, `.venv`, `.scratch`
`hardlinker.py:362-374` (orphan walk), `:573-575` (force delete), vs `:285-294` (source walk)

```python
# source walk — carefully filtered
285:        dirs[:] = [d for d in dirs if not matches_any(d, ..., ignore)]
287:        if skip_hidden_dirs: ... dirs[:] = [d for d in dirs if d not in hidden]

# force delete
```

Every file under `dest/.git`, `dest/.venv`, `dest/.scratch` is by construction "not linked this

**Fix:** apply `matches_any` + the hidden-dir skip in the orphan walk, and hard-refuse any path

### P1-9 — Import-time `httpx2.Client()` makes the whole package unimportable on a host whose `no_proxy` contains `[::1]` (reproduced)
`src/multimodal_rag/utils/pcai_model_classes.py:174`

```python
174: _SHARED_HTTP_CLIENT = httpx2.Client()      # trust_env=True (default) -> reads HTTP(S)_PROXY / NO_PROXY
```

Reproduced on this very checkout: with `no_proxy=127.0.0.1,localhost,::1,[::1]` (this host's
shell), `httpx2` 2.13.1 raises `InvalidURL: Invalid port: ':1]'` while parsing the bracketed IPv6
literal, so `import multimodal_rag` → `dataset_manager` → `rag_system` → `pcai_model_classes`
dies at import. Effect measured: **65 pytest collection errors, 0 tests run**; the app cannot
start either. Clearing the proxy vars restores the full green suite (1571 passed).

Two secondary problems in the same line: (a) the client is never closed and is built at import
(import-time side effect), and (b) it is the **in-cluster** client (`_client_verify(remote=False)`),
yet it honours an operator's `HTTP_PROXY` — in-cluster model traffic would be routed through it.
The module already contains the correct pattern 20 lines below: `_shared_remote_http_client()`
builds lazily under a lock; the fetch paths elsewhere even do `trust_env=not pinned.pin_active`
(`rag_system.py:1015`, `dataset_manager.py:1150`, `mcp_server.py:266`).

**Fix:** build lazily like `_shared_remote_http_client()`, with `trust_env=False` for the
in-cluster client (and add a module-level `close()`).

## Cross-validation found 1 BLOCKER + 13 MAJOR in the fresh fixes — all closed

Two direction-matched reviews ran against the *fixes*, not the audit. They found real defects that a
green suite could not see:

- **BLOCKER** — P3-8's `readOnlyRootFilesystem` on qdrant left `/qdrant/snapshots` unwritable
  (snapshots would fail, possibly at startup). Fixed with an emptyDir in all three charts.
- **PDB semantics were wrong three ways**: `maxUnavailable: 1` on a 1-replica workload computes
  `disruptionsAllowed = 1` — it *permits* evicting the only pod while looking protective; a 2-peer
  qdrant loses raft quorum under it; and the API selector also matched every CronJob pod, so a cron's
  30-minute qdrant gate would zero the budget and block a drain. New rule: no PDB below 2 replicas,
  qdrant `maxUnavailable` forced to 0 below 3 peers, and the API PDB selects a dedicated
  `app.kubernetes.io/component: api` label proven absent from cron pods by render.
- **P2-13 was half-done**: the guard tested only `security.apiKey`, so apiKey-pinned +
  mediaTokenSecret-empty still minted a new media token per render, silently. Both keys are now
  covered, and two renders of the same pinned values are proven byte-identical.
- **`podDisruptionBudget` was the only nil-unsafe key** — `--set podDisruptionBudget=null` (the
  shape `--reuse-values` produces on a first upgrade) failed the render. Guarded.
- **P1-4 was still bypassable**: with no operator signal, *any* valid realm token satisfied the
  precondition, so a token-holder could rotate the header and mint fresh throttle buckets. Each
  candidate is now checked against its own name and the XFF chain requires the operator signal.
- **MCP `end_short_term_memory` skipped the D15 ACL gate** its siblings all call, and skipped the
  password proof REST requires. Both added.
- **`filter.py`'s shared AsyncClient had no event-loop guard** — safe on stock Open WebUI (one loop
  per worker process) but it fails "attached to a different loop" on any multi-loop host, hidden by
  the fail-open path. Now pinned and rebuilt on mismatch.
- Plus: P2-5's allowlist move needed a warning (an allowlist excluding the own host silently breaks
